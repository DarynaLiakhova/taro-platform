# Доступы и видео уроков: защита на стороне базы

Дата: 2026-11-18 · ветка `fix/access-and-videos`

## Зачем

Запуск для первых платящих учениц. Сейчас ученица может сама открыть себе ступени
(поля `owned`, `fbUntil`, `free`, `sessions` лежат в её профиле `u/…`, который она пишет сама),
сама «подтвердить» свою заявку на оплату (`pr/…`, статус `st`) и видит ссылки на видео всех
ступеней (они в общей записи `p/program`). Правила в `supabase/setup.sql` проверяют только
владельца записи (`owner`), но не её адрес (`path`).

## Цели

- Доступы ученицы меняет только Лена (мастер). Ученица их видит, но не меняет.
- Заявку на оплату ученица может только создать со статусом «ждёт»; применяет её только Лена.
- Ссылку на видео ступени база отдаёт только тем, у кого ступень открыта.
- Защита — правилами доступа (RLS) в Supabase, а не только в коде страницы.
- Существующие доступы учениц переносятся автоматически.
- Для ученицы и Лены всё выглядит и работает как раньше.

## Не цели (потом)

- Конспекты и тексты квестов остаются в общей `p/program` (защищаем только видео).
- Подделка прогресса (`cur`, текущая ступень/урок) не закрывается.
- Открытое хранилище `chat`, лимиты на расшифровку, нагрузка от опроса — отдельные задачи.

## Подходы

- **А. Новые адреса в той же таблице `docs` + правило по адресу (выбран).** Механизм
  синхронизации страницы не меняется, опрос раз в 4 с сам подхватывает открытый доступ.
- Б. Отдельные таблицы `access` и `lesson_videos`. Чище схема, но странице нужен второй
  механизм загрузки и опроса; правило по адресам для `docs` всё равно нужно из‑за `pr/`.
  Больше кода и риска перед запуском.

## Решение

### Данные

- `a/<uid>` — доступы ученицы: `{owned:[…], fbUntil, free, sessions, appliedReqs:[…]}`,
  `owner = uid` (чтобы она могла читать). Писать может только мастер.
- `v/<n>` — видео ступени n: `{videos:{<id урока>: <ссылка>}}`, `owner = null`.
  Читает мастер или тот, у кого ступень n открыта. Пишет только мастер.
- `p/program` — программа без поля `video` у уроков.
- Старые поля доступа в `u/…` не удаляются миграцией (чтобы не уронить открытые старые
  вкладки); новая страница их игнорирует и при следующей записи профиля не сохраняет.

### Кто видит ступень (функция `has_stage(n)`, security definer)

- мастер — всё;
- `free = true` в `a/<uid>` — всё;
- ступени 1–6 — если n есть в `owned`;
- ступень 7 — если в `owned` есть все 1–6 (решение Дарины: «подарок за пройденный путь»).

Аккаунт Дарины (сейчас без оплат по почте в коде) получает `free = true` в миграции.

### Правила (дополнительные, `as restrictive`, поверх существующих)

- Чтение `v/n` — только `is_master() or has_stage(n)`.
- Запись/удаление не‑мастером разрешены только по адресам:
  `u/<свой id>`, `s/<свой id>~…`, `m/<свой id>~…`, `n/…`,
  `pr/…` — только если `data.u = свой id` и `data.st = 'wait'` (и для старой, и для новой версии строки).
  Всё остальное (`a/`, `v/`, `pay/`, `p/`, чужие адреса) — только мастер.

### Миграция `supabase/access-migration.sql` (можно запускать повторно)

1. Функции `has_stage`, проверка адреса, новые правила.
2. Для каждой ученицы с `u/…` создаётся `a/<uid>` из её текущих полей
   (`on conflict do nothing` — повторный запуск не затирает то, что Лена уже поменяла).
3. Аккаунту Дарины ставится `free = true`.
4. Видео из `p/program` раскладываются по `v/1…v/7` (только если в программе ещё есть
   ссылки), затем удаляются из `p/program`.
5. Проверочный запрос: ученицы, у которых открытые ступени не подтверждены оплатами
   (`pay/…`) — Лена просматривает список глазами (на случай, если кто‑то уже подправил себе доступ).

### Страница `index.html`

- Сохранение: доступы пишутся в `a/<uid>`, видео — в `v/<n>`, `p/program` без видео,
  `u/…` без полей доступа. Ученица пишет только разрешённые ей адреса.
- Загрузка: доступы из `a/<uid>` накладываются на профиль (без записи — пусто);
  видео из `v/<n>` подставляются в уроки.
- Заявки применяет (`syncReqs`) только Лена.
- Тестовая подмена Supabase (`tests/mocks/supabase.js`) повторяет новые правила.

### Порядок выката

SQL и новая страница выкатываются подряд, без паузы: старая страница у Лены подтверждала
бы оплаты по‑старому, а у учениц пропали бы видео.

## Проверка

- SQL: тесты на PGlite (Postgres в Node, пакет для разработки) — настоящие правила из
  `setup.sql` + миграции; ученица не может писать `a/`, `v/`, `pay/`, подтверждать заявку,
  писать чужие адреса; видит видео только своих ступеней; миграция переносит доступы и
  безопасна при повторном запуске.
- Страница: Playwright с подменой — ученица видит свои ступени, замки, прогресс и видео
  оплаченных ступеней; Лена подтверждает заявку — у ученицы открывается ступень и видео.
